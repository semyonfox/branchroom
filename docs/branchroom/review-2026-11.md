# Branchroom review, November 2026

- Status: implemented on `review/branchroom-audit`, from `fb30e24774`
- Reviewed commit: `a8f7265cd0` (`branchroom/main`)
- Inputs: blind reviews by GPT-6.1 Sol and Claude Fable 5.2, and an authorisation review
  by Claude Opus 5.5. The planned DeepSeek V4.1 Flash security review and the GLM-5.3-Flash
  validation of it both hit the OpenCode free usage limit and produced nothing, so the
  Opus matrix was validated by hand. The implementation was cross-reviewed by Claude

- Every item below was checked against the code at the reviewed commit before it was
  accepted. Claims that did not hold are listed under "Dropped".

## Summary

No reviewer found a route that serves restricted objects to someone without a grant.
Storage isolation holds: only `services/branchroom` resolves `RESTRICTED_ROOT`, and every
ordinary Gitea surface resolves storage from the repository row under `[repository] ROOT`.

The real problems are elsewhere:

- the restricted transport does not work on ordinary repositories (gzip bodies, a
  full-store fsck on every push, a 45 second cap on clones)
- failure and lifecycle paths strand restricted stores on disk or leave rows that can
  never be recovered
- three credential and disclosure edges contradict the documented contract (OAuth tokens
  via Basic auth, team read without discovery, `gitea dump` copying restricted stores)
- stored audit rows do not verify against their own hash

Branchroom has no per-file or per-path permissions. The docs already say so and no
reviewer found text claiming otherwise.

## Fix now

Ordered by impact. Each item names who found it.

### Transport

1. **Accept gzip request bodies.** `routers/web/repo/branchroom_githttp.go:209,216` reject
   any `Content-Encoding`. Git gzips upload-pack bodies over 1 KiB, so clones of
   repositories with about 20 or more refs fail with 404. Decode gzip through a reader
   capped at the existing 1 MiB decoded limit. (Fable, proved)
2. **Stop running a full-store fsck on every push.** `receive_commit_policy.go:92` runs
   `git fsck --strict` with a 10 second limit. fsck verifies every object in the store, so
   pushes to any non-trivial repository time out. Run the receive-pack child with
   `-c receive.fsckObjects=true`, which checks only incoming objects, and rely on
   receive-pack's own connectivity check, which runs before the pre-receive hook. Keep the
   ref, ancestry and object-format checks. (Fable, proved by timing)
3. **Make the body deadline real.** `readBranchroomGitHTTPRPCBody` closes the body from a
   timer, but on HTTP/1.1 `Close` waits behind the blocked read. Use
   `http.ResponseController.SetReadDeadline`. Test with a real stalled socket, not a fake
   reader. (Sol, proved)
4. **Separate the upload-pack process limit from the body deadline.** The 45 second limit
   kills `git upload-pack` mid-pack on large clones. Keep 45 seconds for reading the
   request body and for receive-pack. Give upload-pack a 10 minute process limit and
   document both. (Fable, from code)

### Lifecycle

5. **Stop orphaning retired stores.** `ReleaseRepositoryWorkspaceRetention`
   (`workspace_lifecycle.go:348`) deletes `retired` mappings without removing the store.
   Release only `purged` mappings. Let the current real owner purge a workspace whose scope
   was retired, including by transfer. Test with real stores on disk. (Sol, Fable, Opus,
   proved)
6. **Recover stuck `provisioning` rows.** A crash or a `markWorkspaceReady` error leaves a
   row that retry, retire, purge and repository deletion all refuse. On a
   `markWorkspaceReady` error, remove the store and mark the row failed. Treat a
   `provisioning` row older than one hour as abandoned, so retry and purge accept it, and
   give the import a matching hard timeout so a live import cannot outlast that window.
   (Sol, Fable, proved)
7. **Refuse Branchroom on MSSQL.** Lifecycle locks use `FOR UPDATE` only on MySQL and
   PostgreSQL, and SQLite serialises writers itself. MSSQL gets no serialisation at all.
   Fail at startup when Branchroom is enabled on MSSQL. (Fable, from code)

### Authorisation

8. **Reject OAuth2 and Actions tokens sent as Basic credentials.**
   `services/auth/basic.go:72-85` accepts an OAuth2 JWT as a Basic password or username and
   sets `ApiTokenScope`. The gateway then accepts it and skips the 2FA check. Allow only
   `LoginMethod` password Basic or a personal access token in
   `authorizeBranchroomGitHTTPIdentity`. (Fable from code, Opus proved for read)
9. **Make the handoff rule match the docs.** `source_handoff.go:131-146` shows the clone
   URL for a team `read_source` grant without any `discover` grant. Require discovery
   (direct or team) and source read (direct or team). Team `discover` grants, which the
   settings page already offers, then mean something. (Sol proved, Fable, Opus)
10. **Keep restricted stores out of `gitea dump` and other roots.** `cmd/dump.go:264-271`
    packs `APP_DATA_PATH` minus a fixed list that omits `RESTRICTED_ROOT`. Exclude it
    explicitly and log that restricted stores need a separate backup. At startup also
    refuse overlap with local storage paths, `CustomPath` and `StaticRootPath`. (Opus)
11. **Refuse local-path import from inside the restricted root.**
    `services/migrations/migrate.go:51-68` accepts any absolute directory for users who can
    import locally. Compare canonical paths and refuse anything inside `RESTRICTED_ROOT`.
    (Opus)
12. **Validate store IDs.** `modules/branchroom/store.go` accepts any non-empty store ID.
    Require a canonical UUID. (Opus)

### Audit

13. **Make stored audit rows verify.** `Decision.CreatedUnix` and `AuditEvent.CreatedUnix`
    carry the xorm `created` tag, which overwrites the hashed timestamp at insert. Remove
    the tag. Add a test that re-reads rows and walks the chain. (Fable, proved)
14. **Remove the audit conflict retry.** A nested `db.WithTx` that returns
    `ErrAuditConflict` ends the caller's transaction, and the retry runs in autocommit.
    Return the conflict instead. (Fable, mechanism proved, reachable only without row
    locks, which item 7 closes)

### Settings page and startup

15. **Fix the settings script crash.** `web_src/js/features/branchroom.ts:9-11` assumes the
    privacy control exists, and the settings template does not include it, so the page
    script throws before time-window validation runs. Only bind the privacy control when it
    is present. (Fable, from code)
16. **Run the runtime ownership check at startup.** Startup checks only modes, so a root
    the service account cannot write passes and every operation fails later. Reuse the
    runtime check. Correct `self-hosted-demo.md`, which says the root may be owned by root.
    (Fable, from code)

### Docs

17. Correct `implementation-plan.md`, `self-hosted-demo.md` and `README.md` where they
    contradict the code: migration numbers (Branchroom is 352 to 357 in
    `modelmigration/migrations.go`), team, write and expiring grants now exist, the purge
    state exists, the handoff rule, the timeouts, the OAuth rule, what happens on deletion,
    and that site administrators are trusted operators (see deferred item D6).

### Tests

The authorisation fixes get access-matrix tests, not single cases:

- **Gateway matrix.** One table-driven integration test over the four gateway operations
  (upload-pack advertisement and RPC, receive-pack advertisement and RPC) against every
  actor: anonymous, unrelated user, collaborator without grant, team `read_source`
  member, discover only, direct `read_source`, direct `write_source`, owner without
  grants, site admin, Actions token, OAuth2 JWT as Basic password and as username, PAT
  `read:repository`, PAT public-only, PAT `write:repository`, password user with 2FA,
  deactivated user. Each cell asserts the exact status.
- **Handoff matrix.** The same actors against `/{owner}/{repo}/-/branchroom`, including
  team discover plus team read, team read alone and direct read alone.
- **Public surfaces.** For a commit that exists only in the restricted store, assert 404
  on web raw, src, blame, commit, diff, compare and archive URLs and on the REST
  `git/commits`, `git/blobs`, `contents?ref=` and `archive` endpoints.

## Deferred

- **D1. Owner quota race** (Sol, from code). Concurrent provisioning across repositories
  can exceed `MAX_WORKSPACES_PER_OWNER`. It is a resource limit, not an access boundary.
- **D2. Databases from the earlier migration layout** (Sol, Fable). Commit `d9bb0642a3`
  moved Branchroom from 349 onwards to 352 onwards. A database created before that skips
  upstream 349 to 351. The fix depends on whether any such database exists, so it needs
  Semyon's answer first. Renaming `v356.go` to `v361.go` to match their IDs is churn
  without behaviour change.
- **D3. Repairing hooks after a path change** (Fable). The hook embeds `AppPath`, the
  config path and `RESTRICTED_ROOT`, so moving any of them stops pushes until the hook is
  regenerated. This needs a new admin command. Document it until then.
- **D4. Rate limiting route-key holders** (Fable, Opus). A signed-in user with a stale
  route key causes locks and audit writes per request.
- **D5. Audit retention and tamper evidence** (Opus). Repository deletion removes the
  audit chain, and the chain has no keyed anchor. This needs a retention design.
- **D6. Site administrators** (Opus). An admin can impersonate a user and mint a PAT,
  reset a password, or join an owner team. Closing these changes upstream Gitea admin
  behaviour. The docs will say admins are trusted operators instead.
- **D7. Host-level features** (Opus). Editable server-side git hooks and runners on the
  same host can read the restricted root as the service account. Document it.
- **D8. Smaller items.** Disabled feature blocks deletion (Fable), oversize push reports
  404 (Fable), route keys in router logs (Opus), dangling grants after user or team
  deletion (Opus).
- **D9. Dead and redundant code** (Fable). The environment subsystem has no production
  caller, the telemetry client has no collector, several functions and one template are
  unused, and the hook is verified three times per push. Removing the environment
  subsystem is a product decision, so it waits for Semyon.

## Dropped

- **Recheck grants and lifecycle state inside the pre-receive hook** (Opus F7). The hook
  deliberately treats the claimed session as the authorisation boundary
  (`receive_verify.go:107-112`) and the plan documents that one claimed push may finish
  after revocation, retirement or transfer. This is a stated design choice with a bound of
  one push, at most 1 MiB and 45 seconds, not a defect.
- **"Existence oracle" by write-transaction timing** (Opus F9). Distinguishing a known from
  an unknown route key needs the 128-bit key already, so the signal adds nothing.
- **Normal Git, SSH, LFS, web, API, indexer, webhook, Actions, mirror, fork and template
  paths reaching a restricted store** (asked of every reviewer). All three found that these
  resolve storage from the repository row through `models/repo/repo_location.go` and that
  startup refuses overlap with `[repository] ROOT` (`modules/setting/branchroom.go:46-56`).
  `_branchroom` cannot be a username (`modules/validation/helpers.go:28` requires a leading
  alphanumeric), and cache keys use the `branchroom-store-<uuid>` managed ID
  (`modules/branchroom/store.go:28`), disjoint from public repositories. The public-surface
  tests above pin this instead of a code change.
- **GraphQL.** Not present in this codebase.

## Implementation verification

Fix-now items 1 to 17 are implemented. The gateway and handoff matrices assert every
actor and operation cell. Public web and REST requests use an object found only in the
restricted store.

The REST `git/blobs/{sha}` 404 assertion is skipped. The existing handler in
`routers/api/v1/repo/blob.go` returns 400 for any object lookup error, including an
unknown SHA. The regression asserts that existing 400 response without changing the
public API. Every other requested public endpoint returns 404.

## Cross-review of the implementation

The implemented branch was reviewed against this plan. It confirmed the transport
fixes and the access matrix, and found these problems, all fixed on the same branch:

- **Transferred repositories could not be deleted.** Releasing only `purged` mappings
  was right, but the settings page hid retired scopes, so the new owner had no purge
  control, and deletion returned 500 after closing pull requests. The page now shows
  retired scopes with an unpurged workspace and only a purge control. Deletion checks
  retention before any side effect, the web flow flashes a message and the API returns
  409.
- **Any restricted root under the work path was refused.** The new overlap check
  compared against `StaticRootPath`, which defaults to the work path, and config load
  runs for every subcommand, so `gitea serv` and `gitea hook` failed too. The check now
  covers only the served `public`, `templates` and `options` directories.
- **Abandoned provisioning had no control on the page.** Retry and purge now show for
  it.
- **`gitea dump` still packed restricted stores through a symlinked data path.** The
  dump now also excludes the root as seen through each walked directory.
- **FastCGI broke the read deadline.** Branchroom now refuses to start under FastCGI.
- **Local import failed when the restricted root was missing.** A missing root is now
  skipped.
- **A late abandoned import could delete the store a retry had made ready.** Each retry
  now gets a fresh store ID, and the ready and failed transitions check it.
- **Chunked gzip input was unbounded.** The compressed side is now capped at 1 MiB.

`receive.fsckObjects` rejecting legacy object defects is documented rather than relaxed.

## Found by the full checks

Two pre-existing bugs surfaced only outside the test suites the reviewers ran:

- **A fresh install with Branchroom enabled would not start.** Config load required
  `[repository] ROOT` to exist, but Gitea creates it later. Both Docker images died at
  startup. The overlap check now resolves the nearest existing ancestor.
- **Branchroom never worked on PostgreSQL.** `audit_head_hash` and `previous_hash` were
  `CHAR(64) DEFAULT ''`, which PostgreSQL pads with spaces, so the first audit event of
  every scope failed validation and scope creation failed. Migration 358 converts both to
  `VARCHAR(64)`. The Branchroom integration suite had only run on SQLite.

## Follow-up on the deferred items

Each deferred item was checked against the code and the live LAN instance before a
decision.

| Item | Decision |
| --- | --- |
| D1 owner quota race | Closed. Only owners provision, the limit protects their own disk, and SQLite serialises writers. Lock the owner row if PostgreSQL is used in anger. |
| D2 earlier migration layout | Closed. The only real database was created after the renumbering and already has upstream 349 to 351. |
| D3 hook repair after a path move | Done. `gitea doctor check --run branchroom --fix` reinstalls hooks through an explicit replace path. Install itself still refuses a differing hook. |
| D4 rate limiting route-key holders | Kept deferred until there are more users or internet exposure. Locks are held only for authorisation. |
| D5 audit retention and tamper evidence | Done in part. Deletion keeps the audit chain, and the doctor check verifies every chain. A keyed anchor is skipped because database operators are outside the threat model. |
| D6 site administrators | Accepted as trusted operators, as documented. Upstream impersonation cannot be disabled. |
| D7 host hooks and runners | Done. Branchroom refuses to start with `DISABLE_GIT_HOOKS = false`. Runners remain documented. |
| D8 smaller items | Deletion while disabled explains how to proceed, an authorised oversized body gets 413, admin deletion no longer returns 500. Route keys in router logs and dangling grants stay as they are. |
| D9 dead and redundant code | Done. The environment store, preflight scanner, telemetry client, workspace dialog and dead session functions are gone, as is the advertisement-time hook check. `authorizeWorkspaceRead`, `getScopeMetadata` and `GetWorkspaceByRouteKey` stay as unit-test entry points into shared production code. |
